# api

The HTTP API — users, problems, submissions. C# and ASP.NET Core on .NET 10, Minimal APIs.

One project, never projects by layer — as concerns arrive they become folders inside it. This mirrors `/executor`, which is one package with modules. The API deliberately has no ability to execute submitted code: it delegates to the executor over HTTP and stores what comes back.

It requires the .NET 10 SDK or later, pinned in `global.json`. The suite starts its own Postgres with Testcontainers, so it needs Docker — which this repository already requires everywhere else.

## Commands

Run from this directory. Both act on `LeetLingo.slnx`, the only solution here.

| | |
| --- | --- |
| Build | `dotnet build` |
| Test | `dotnet test` |
| Run | `dotnet run --project src/LeetLingo.Api` |

## Layout

```
api/
  src/LeetLingo.Api/
    Program.cs          every route the API serves
    LeetLingoContext.cs the database, its mapping and its seed
    Migrations/         generated, versioned with the repository
    Problems/           the problem concern
  tests/LeetLingo.Api.Tests/
```

Tests drive the API in process over real HTTP through `WebApplicationFactory`, with real dependency injection, real EF Core and a real Postgres the suite starts and owns. They never call a handler directly, and test names are sentences, as they are throughout `/executor`.

## Changing the schema

`dotnet ef` is a local tool, restored from `dotnet-tools.json`:

```
dotnet tool restore
dotnet ef migrations add <Name> --project src/LeetLingo.Api
```

EF writes `/// <inheritdoc />` onto everything it generates. This repository carries no comments, XML doc comments included, so delete those lines from the generated files before committing. Leave the `// <auto-generated />` line at the top of the designer and snapshot files — it is a marker the compiler reads, not prose, and removing it exposes generated code to `TreatWarningsAsErrors`.

The seed lives in `Problems/TheSeededCatalogue.cs` and reaches a database only through a migration's literal. Changing it means a new migration; `The_catalogue_comes_from_the_migration_and_is_the_same_on_every_fresh_database` fails if you forget.

Nothing migrates the database at startup, by design. The suite migrates the Postgres it owns; bringing the stack up is Compose's job.

`appsettings.Development.json` points at a local Postgres so `dotnet run` works on the host. It is a development default only — Compose supplies its own by environment.
